# ADR-0001：按顺序向原生编辑器交付输入

日期：2026-09-24。状态：采用；实现及验收由 [#2](https://github.com/qinyin233/rupora/issues/2) 跟踪。

## 问题

同一原生事件批次可能包含多次格式操作及其前后的文字。按快捷键优先级只选择一个
操作会丢掉其他命令；整批消费相同按键会把两次加粗变成一次。未消费的 Windows
Ctrl+K 还可能进入 TextEdit 的删除到段尾操作。只检查最终字符没有减少不足以发现错误。

## 决策

- 保留 egui TextEdit 作为文字、导航和组合输入的执行者，不在 App 重写第二套文本编辑器。
- App 作为原生输入适配层，按事件位置分段交付；每段的文字输入先由 EditorSurface
  处理，再执行该段末尾的应用命令。实际编辑器 UI 处理完毕才确认该段，隐藏窗口只运行
  logic 时不能假定输入已消费。
- 在 eframe 的 `raw_input_hook` 中、egui 捕获本帧预算之前，为分段处理预留渲染 pass。
  每帧最多处理 8 个 pass，剩余输入继续绑定原文档，安排后续重绘。
- App 的待交付记录可以携带原文档 ID 和光标书签副本。它们只用于恢复交付上下文；
  EditorSurface 仍独占当前光标、选择、IME 与编辑事务，Document 独占正文与历史。
- 保存、新建、查找等窗口命令是交付边界：先完成前面的编辑及效果，再执行命令；后续
  输入经原生入口重新交付，遵守命令执行后的文档和焦点。
- 鼠标、焦点、文件拖放等原生包不能通过只替换 `InputState.events` 来伪造重放，
  因为 egui 在开始 pass 时就计算了其他输入状态。延迟包必须通过 RawInput 入口重放。
- IME 预编辑和候选确认也是交付边界：先处理前面的普通输入，再建立组合基线。
  Windows 的空预编辑与紧随其后的候选确认保留为同一段；提交与下一轮预编辑分开。
  鼠标按住、滚动或焦点转换等不能使用编辑器 pass 的混合包，在 RawInput 入口拆分；
  关闭和文件拖放等没有事件位置的元数据通过独立尾包交付一次，避免提前执行。

## 代价与限制

App 增加了原生包的调度状态，但不取得编辑算法和正文状态的所有权。每帧 pass 上限是
计算预算，不是输入队列的硬内存上限；不能用丢弃文字来掩盖超预算输入。重复窗口状态
和无编辑意义的包应避免产生无效积压。测试应区分同帧排空与跨帧继续交付。

事件注入能够验证应用状态机，不能证明真实系统输入法和窗口管理器行为；这些另由
[#6](https://github.com/qinyin233/rupora/issues/6) 验收。任何后续替代实现都必须保留
命令顺序、原文档归属、方向选区、历史边界、隐藏窗口确认和关闭时的输入保护。
